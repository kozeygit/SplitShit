# System Design Document: Mobile-to-Web Bill Splitter

## 1. Core Architecture Strategy

1. **Host-First Data & Final Authority:** The mobile app handles historical memory and math. The web view uses pre-added guest profiles and deterministic contracts.
2. **Transient Cloud Mailbox:** The cloud database acts purely as a temporary staging area for claims. Active tables use a 24-to-48 hour automatic self-destruct cycle (TTL).
3. **The Host Review Gate:** Web claims are queued in a staging area on the host's device. The host must review, resolve overlaps, and commit claims in a batch process before the local SQLite database updates.
4. **Zero-Friction Web Experience:** Guests use a "Multi-Select Gateway" to claim for themselves and their dependents in one pass, with the ability to edit their submissions via a local device ID.


---

## 2. Cloud Database Structure (Supabase)

### A. `bill_sessions`

* `session_token` (String, Primary Key)
* `status` (String: "active", "locked", or "canceled")
* `bill_name` (String)
* `items` (JSON Array: food items, prices, and quantities)
* `host_push_token` (String)

### B. `session_payers`

* `id` (Auto-generated UUID)
* `session_token` (String, Foreign Key)
* `payer_id` (String/Integer from local app)
* `name` (String)
* `submitted_at` (Datetime, defaults to NULL)

### C. `bill_claims`

* `id` (Auto-generated UUID)
* `session_token` (String, Foreign Key)
* `device_id` (String: unique ID generated by guest's browser to map edits)
* `payer_id` (String/Integer)
* `item_id` (String/Integer)

## 3. Data Flow & Operational Lifecycle

1. **Push Snapshot (Generate Link):** The host generates a unique code (e.g., `qR7x9p`). The mobile app pushes the receipt into `bill_sessions` and the guest list into `session_payers`.
2. **Download Init State (The Web View):** Friends open the link. They select their names via the "Multi-Select Gateway". A hidden `device_id` is generated and saved to their browser's `localStorage`.
3. **Append Final Claims (Submit):** Guests check off items line-by-line. Tapping "Submit" executes a three-step transaction:
    * **Clear:** `DELETE` existing rows in `bill_claims` matching their `device_id` and selected `payer_id`s.
    * **Insert:** `INSERT` new rows into `bill_claims` for every checked item.
    * **Flag:** `UPDATE` the `session_payers` table, setting `submitted_at = NOW()` for their selected names.

4. **The Notification:** A Supabase Edge Function listens strictly for updates to `session_payers.submitted_at`. When triggered, it reads the `host_push_token` and fires an Expo Push Notification to the host.
5. **Pull & Review (The Review Gate):** The host opens the app. The app downloads the updated rows from `bill_claims`. The host reviews a summary screen, resolves overlaps, and taps "Commit All."
6. **Lock & Nuke:** Committing updates the local SQLite database and changes the cloud `status` to `locked` (late guests see "Bill Finalized"). The cloud data auto-deletes 24-48 hours later.
    * *Restart Flow:* If the host edits the bill mid-session, they trigger a "Hard Kill & Re-issue," updating the old session status to `canceled` and generating a new link.

## 4. Master Implementation Roadmap

### Phase 1: Local Mobile Prep

* Update local SQLite tables to track the "awaiting web claims" state.
* Build the "Review Gate" UI screen to hold incoming web claims.
* Implement the "Hard Kill & Re-issue" link invalidation logic.

### Phase 2: Cloud Provisioning

* Create a Supabase project and the three tables.
* Configure the 24-48 hour TTL auto-delete script.
* Write the Edge Function to trigger Expo Push Notifications based on `session_payers.submitted_at` changes.

### Phase 3: Web Application Logic

* Build the Multi-Select Onboarding screen (with the "Change Name" escape hatch) and generate the local `device_id`.
* Build the Checklist UI that pulls `items` from `bill_sessions`.
* Wire up the Submit transaction (Delete -> Insert -> Update `submitted_at`).

### Phase 4: Connecting the Bridge

* Setup Expo Notifications in the React Native app.
* Add deep-linking to route notification taps directly to the specific bill's "Review Gate."
* Write the local ingestion script to map the `bill_claims` rows back into the host's required arrays.
